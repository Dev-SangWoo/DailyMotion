# 지하철 혼잡도 매핑 설계 (서울교통공사 ↔ ODSAY)

> 목적: 서울교통공사_지하철혼잡도정보와 ODSAY 경로 데이터를 **안전하게 1:1 매핑**해서  
> Logic 1.1/1.2/2.2/3.1에서 사용할 "구간·시간대별 평균 혼잡도" 베이스라인을 구축한다.

---

## 1. 노선 매핑 (확정)

- 방식: **매핑 테이블(Dictionary/JSON)** 방식
- ODSAY 기준:
  - 필드: `lane.subwayCode` (Type: Number, 예: `1`, `2`, `7` 등)
- 서울교통공사 기준:
  - 필드: `호선` (또는 `LINE_NUM`) (Type: String, 예: `"1호선"`)

### 매핑 테이블 예시

```json
{
  "1": "1호선",
  "2": "2호선",
  "3": "3호선",
  "4": "4호선",
  "5": "5호선",
  "6": "6호선",
  "7": "7호선",
  "8": "8호선"
}
```

- 예외 처리:
  - `subwayCode`가 위 테이블에 없으면(예: 9호선, 경의중앙선 등)
    - 서울교통공사 혼잡도 데이터에 정보가 없는 것으로 간주
    - → 해당 구간은 `"혼잡도 정보 없음"`으로 처리하고, Fallback 로직(기본값/다른 데이터 소스)을 사용한다.

---

## 2. 역 매핑 (중요 ⚠️)

- 원칙: **역 이름(String)으로 비교하는 방식은 금지**
  - 예: `"총신대입구"` vs `"총신대입구(이수)"` 등 수많은 예외 케이스 존재
  - 이름 기반 매칭은 MVP 일정에 리스크가 크므로 사용하지 않는다.

- 대신, **고유 ID 기반 매핑**을 사용한다.

### 목표: MasterStationMap 구축

> "ODSAY 역 ID"와 "서울교통공사 역 ID"를 연결하는 **MasterStationMap.json (또는 DB 테이블)**을  
> 단 한 번만 구축하고, 이후에는 이 매핑을 통해 100% 정확하게 혼잡도 데이터를 참조한다.

#### 2.1 ODSAY 고유 ID 필드 확인

- ODSAY API 응답에서:
  - `segment.startName` (역 이름) 말고,
  - 해당 역의 **고유 ID**를 나타내는 필드 (예: `stationID`, `stationCode`, `globalStationID` 등)를 찾는다.
- 이 필드를 `odsayStationID`로 사용한다.

#### 2.2 서울교통공사 고유 ID 필드 확인

- 서울교통공사 혼잡도 데이터에서:
  - `출발역`(역 이름) 말고,
  - 고유 ID 필드(예: `역번호`, `STATION_CD`)를 사용한다.
- 이 필드를 `seoulStationID`로 사용한다.

#### 2.3 MasterStationMap 구조 (예시)

```json
[
  {
    "odsayStationID": "222",
    "seoulStationID": "0222",
    "debugName": "강남"
  },
  {
    "odsayStationID": "432",
    "seoulStationID": "0424",
    "debugName": "총신대입구(이수)"
  }
]
```

- `debugName`은 사람이 보기 좋은 이름일 뿐, 실제 매칭은 **ID 기준**으로만 수행한다.

#### 2.4 매핑 로직 요약

1. ODSAY 경로 응답에서 `odsayStationID` (예: `"222"`)를 가져온다.
2. `MasterStationMap`에서 `"222"`를 조회해 대응하는 `seoulStationID` (예: `"0222"`)를 찾는다.
3. 이 `seoulStationID` + 노선명(예: `"2호선"`) 조합으로  
   서울교통공사 혼잡도 데이터에서 정확한 행을 조회하고, 해당 시간대 컬럼의 값을 혼잡도로 사용한다.

> 이 ID 기반 방식을 사용하면, 역 이름 표기 차이와 관계없이  
> 100% 정확한 혼잡도 매핑이 가능해지고, 서비스 안정성이 확보된다.

## 3. 시간대 매핑 & 혼잡도 임계값 (확정)

### 3.1 시간대 해상도: 30분 버킷

- 공공데이터가 이미 `5시30분`, `6시00분`과 같이 **30분 단위 컬럼**으로 내려오기 때문에,
  - 현재 시각을 30분으로 내림(floor) 한 버킷을 사용한다.
- 규칙:
  - `bucket = floorTo30min(now)`  
    - 예: 07:12 → 07:00, 07:44 → 07:30
  - 해당 버킷 컬럼 값이 있으면 그 값을 사용.
  - 값이 없으면:
    - 1차: 직전 30분 버킷으로 Fallback (예: 08:30 없으면 08:00 참조)
    - 그래도 없으면 `"혼잡도 정보 없음"`으로 처리.

### 3.2 혼잡도 임계값 (퍼센트 → 등급)

- MVP 기준 임계값:
  - `0 ~ 40`   → `LOW`
  - `40 ~ 70`  → `MEDIUM`
  - `70 ~ 90`  → `HIGH`
  - `90 이상`  → `VERY_HIGH`
- 출시 후:
  - 실제 클릭률/이탈률/피드백을 보고 위 임계값을 튜닝한다.

### 3.3 메시지/필드 설계

- 내부 표현:
  - `congestionValue` : 원본 혼잡도 값 (float, %)  
  - `congestionLevel` : `LOW` / `MEDIUM` / `HIGH` / `VERY_HIGH`
- 사용자 노출:
  - 기본적으로 **라벨 + 퍼센트 둘 다**를 사용:
    - 예: `"현재 구간 혼잡도: 높음 (87%)"`
